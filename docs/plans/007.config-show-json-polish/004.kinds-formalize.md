# Step 004 — formalize new `Kinds` constants

## Goal

Add two new constants to the `Kinds` registry in `errors.py` — `USAGE_CONFIRMATION_REQUIRED` and `CLI_BAD_ENUM` — and update the two existing raise sites that currently use a free-string `kind` or the wrong `Kinds` constant. Both new kinds map to code 1 (`EXIT_USAGE`).

## Files to create or modify

- `src/code_index/errors.py` (edit — add two `Kinds` constants)
- `src/code_index/cli.py` (edit — update the `index rebuild --yes` raise site and the `search --mode` enum-validation raise site)
- `tests/test_new_kinds.py` (new)

## Signatures

```python
# src/code_index/errors.py — Kinds class additions

class Kinds:
    # ... existing entries unchanged ...
    USAGE_CONFIRMATION_REQUIRED: str = "usage.confirmation_required"
    CLI_BAD_ENUM: str = "cli.bad_enum"
```

No new exit-code constants — both map to the existing `EXIT_USAGE = 1`.

## Raise-site updates

### `index rebuild --yes` confirmation gate

**Before** (per `006.sync-symbols-graph/002.rebuild-cli.md` lines 28, 44, and the resolved approach in `006/002.context.md`): the raise site uses a free-string `kind="usage.confirmation_required"`, like:

```python
raise CodeIndexError(
    code=EXIT_USAGE,
    kind="usage.confirmation_required",
    message="index rebuild is destructive; pass --yes to confirm",
)
```

**After:**

```python
raise CodeIndexError(
    code=EXIT_USAGE,
    kind=Kinds.USAGE_CONFIRMATION_REQUIRED,
    message="index rebuild is destructive; pass --yes to confirm",
)
```

The envelope `kind` string is identical (`"usage.confirmation_required"`); the change is sourcing from the registry rather than a literal. No behavior change for callers; Phase 6's tests still pass.

### `search --mode` enum validation

**Before** (per `005.search/002.context.md` lines 33–54, the resolved approach in that step was "reuse `Kinds.CONFIG_BAD_ENUM`"):

```python
raise CodeIndexError(
    code=EXIT_CONFIG,
    kind=Kinds.CONFIG_BAD_ENUM,
    message=f"invalid --mode value: {value}; expected bm25|dense|hybrid",
)
```

OR (if Phase 5's coder chose Typer's enum / `Literal` and let Typer surface the usage error itself): no explicit raise, Typer emits exit 2 with its own message.

**After** (either way Phase 7 normalizes the explicit-raise form):

```python
raise CodeIndexError(
    code=EXIT_USAGE,
    kind=Kinds.CLI_BAD_ENUM,
    message=f"invalid --mode value: {value!r}; expected one of bm25, dense, hybrid",
    detail={"flag": "--mode", "value": value, "expected": ["bm25", "dense", "hybrid"]},
)
```

Note the code change too: `EXIT_USAGE` (1), not `EXIT_CONFIG` (2). The CLI-flag enum is a usage error, not a config error.

If Phase 5's coder deferred to Typer's built-in enum validation (no explicit raise), step 004 replaces it with an explicit check + raise so that:

- The kind string `"cli.bad_enum"` is emitted under `--format json`.
- The exit code is 1, not Typer's default 2.
- The message includes the rejected value and the allowed set.

Coder verifies which form Phase 5 produced by reading `src/code_index/cli.py`'s `cli_search` body before editing. Both starting forms are addressed by the same target shape.
