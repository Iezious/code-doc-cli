# 003 — context

Narrow notes for the backend-wrapping step. Feature-wide framing is in [`context.md`](context.md).

## Exception class scope: why `Exception`, not `BaseException`

`KeyboardInterrupt` and `SystemExit` are `BaseException` subclasses but not `Exception` subclasses. Wrapping them would swallow user-initiated cancel or interpreter-exit signals. Catch `Exception` only.

`CodeIndexError` is itself an `Exception` subclass, so the naive `except Exception` would re-wrap our own raises. The wrap shells therefore special-case `CodeIndexError`:

```python
try:
    ...native fastembed call...
except CodeIndexError:
    raise
except Exception as exc:
    raise CodeIndexError(EXIT_BACKEND, Kinds.BACKEND_..., ...) from exc
```

This is the standard "do not re-wrap our own errors" pattern. The test case asserts the identity.

## Why two distinct kinds

`errors-and-exit-codes.md` enumerates `backend.model_download_failed` and `backend.encode_failed` as separate entries even though both share code 20. The distinction is semantic: download failures are transient and user-fixable (network, disk space, model name typo); encode failures usually indicate an environment problem (ONNX runtime mismatch, OOM, malformed input). Agents key on `kind`, not `code`, to choose retry strategies.

`__init__` and `from_config`-time construction errors map to `BACKEND_MODEL_DOWNLOAD_FAILED`. `encode`-time errors map to `BACKEND_ENCODE_FAILED`. The boundary is "did the backend successfully initialize?", not "did fastembed do a network call?". A constructor failure that didn't involve a download (e.g. ONNX runtime missing) still maps to `BACKEND_MODEL_DOWNLOAD_FAILED` — the kind name is slightly imprecise but the contract is pinned in `errors-and-exit-codes.md` and Phase 7 does not redesign it.

## `monkeypatch` strategy for tests

Phase 2's `tests/test_fastembed_backend.py` (per `002/context.md` decision 2) uses real downloads into `tests/.cache/fastembed/`. Phase 7's wrapping tests should NOT depend on the cache — they specifically test failure paths.

Approach:

1. For `__init__` wrap tests: `monkeypatch.setattr("fastembed.TextEmbedding.__init__", raising_init)` where `raising_init` raises a chosen exception. Confirm the actual import path Phase 2 used by reading `src/code_index/embeddings/fastembed.py` at coding time — the exact attribute may differ (e.g. `fastembed.TextEmbedding` vs `fastembed.embedding.TextEmbedding`).
2. For `encode` wrap tests: construct a `FastembedBackend` whose `_model` attribute (or whatever Phase 2 named the wrapped library object) is replaced post-construction with a stub raising on `.embed(...)`. To avoid the real construction cost, also `monkeypatch` `__init__` to a no-op that just sets `self.name`, `self.dim`, and the stub `_model`.
3. For the "`CodeIndexError` not re-wrapped" test: use a stub `_model.embed` that raises `CodeIndexError(EXIT_BACKEND, Kinds.BACKEND_ENCODE_FAILED, "already wrapped")` directly.

If Phase 2 named the inner model attribute something different (`_engine`, `_te`, etc.), adapt — the test file's docstring documents whichever name the implementation uses.

## What the `detail` dict carries

Per `errors-and-exit-codes.md` "JSON error envelope":

> `detail` is freeform per `kind`. Agents that recognize the `kind` may read it; others ignore it safely.

For both backend kinds, this step pins:

- `model`: the configured model string (for `__init__` / `from_config` errors) or `self.name` (for `encode` errors).
- `cause`: `str(exc)` — the native exception's message.
- `type`: `type(exc).__name__` — the native exception's class name.
- For `encode` errors only: `batch_size`: the length of the failing batch (helps debug OOM-style failures).

All values are JSON-serializable strings or ints. No nested objects, no non-ASCII.

## Pass-through for the Voyage stub

`from_config`'s wrap layer must not interfere with the existing Voyage stub raise:

```python
if config.embed_backend == "voyage":
    raise CodeIndexError(EXIT_USAGE, Kinds.CLI_NOT_IMPLEMENTED, "voyage backend not available in this build (lands in Phase 7)")
```

The `except CodeIndexError: raise` clause covers this — the Voyage stub's `CodeIndexError` propagates unchanged. Since this is Phase 7 itself, the "lands in Phase 7" message is now stale; however, Phase 7's scope (per `context.md` "Out of scope") explicitly excludes Voyage. The roadmap'd Voyage backend is the new home for that work. Do **not** touch the Voyage stub's wording in this step — leave the message as-is. The cli.md / mvp-scope.md fold-in that retires the "lands in Phase 7" wording is for the architect at finalization.

## What this step does NOT do

- Does not implement the Voyage backend.
- Does not modify the `EmbeddingBackend` Protocol.
- Does not change batching logic or the `encode` return-shape contract.
- Does not add new kinds beyond the two already in `Kinds` from Phase 1.
- Does not wrap exceptions inside the indexer (`indexer.build`); the indexer already catches per-file failures separately. Phase 7's wrap is at the backend boundary only.
