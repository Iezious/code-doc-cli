# 002 — context

Narrow notes for the `init` JSON output step. Feature-wide framing is in [`context.md`](context.md).

## `force_used` definition

`force_used` answers the question "did `--force` actually do something destructive?", not "was `--force` passed?". The distinction:

- Fresh init, no `--force`: `force_used == False`.
- Fresh init, `--force` passed: `force_used == False` (no prior file existed; the flag was a no-op).
- Re-init over an existing config, `--force` passed: `force_used == True`.
- Re-init over an existing config, no `--force`: this case raises (Phase 4 contract), so the JSON envelope is an error envelope, not the success shape.

This makes `force_used` a useful field for agents: it tells them whether the call mutated existing state.

## Path string format

`config_path` and `gitignore_path` are emitted as absolute path strings with forward slashes (per `context.md` "Cross-cutting constraints"). Use `pathlib.Path(...).resolve().as_posix()`. Do not embed Windows backslashes in the JSON output.

## Suppressing text-mode chatter under `--format json`

Phase 4's text-mode `init` prints messages like "wrote docs/.helpers/config.toml". Under `--format json`, stdout must carry exactly one JSON document. The branch must therefore not call `write_result_stdout` with the text-mode lines; instead it emits the JSON document once, at the end, after the writes succeed.

Stderr stays clean too — no progress lines under `--format json` (per `cli.md` "Output streams and logging"; `--quiet` is independent of this, but JSON mode also implies "machine consumption" and existing convention is to keep stderr empty on success). If Phase 4 emitted stderr progress lines for `init`, suppress them under `--format json` in this step.

## What Phase 4 already computes

Per `004.walker-and-build/002.init.md`, the body computes:

- `project_root` = CWD.
- `helpers_dir` = `project_root / "docs" / ".helpers"`.
- `config_path` = `helpers_dir / "config.toml"`.
- `gitignore_path` = `helpers_dir / ".gitignore"`.
- `project_name` = `--name` value or `project_root.name`.

The JSON branch reuses these locals; nothing new is computed.

## Phase 4 refuse-kind compatibility

The "refuse without `--force`" envelope test does not assert a specific `kind` — only that the envelope structure is `{"error": {"code", "kind", "message", "detail"}}` and that it round-trips through `json.loads`. This protects against Phase 4 having picked a different kind than Phase 7's planner would expect; the cross-subcommand DoD (step 005) does the strict per-subcommand assertions.

## What this step does NOT do

- Does not touch text-mode output.
- Does not redesign the refuse-without-`--force` raise path.
- Does not modify `init` flag parsing or argument validation.
- Does not add new fields beyond the four pinned in `context.md` decision 3.
