# 004 — context

Narrow notes for the kinds-formalize step. Feature-wide framing is in [`context.md`](context.md).

## Touching code authored by prior phases

This step is the only Phase 7 step that modifies code Phase 5 and Phase 6 authored. Specifically:

- `cli_index_rebuild` body (Phase 6 — `006.sync-symbols-graph/002.rebuild-cli.md`).
- `cli_search`'s `--mode` enum validation (Phase 5 — `005.search/002.search-cli.md` + `005.search/002.context.md`).

Both touch sites are localized — one `raise` statement each (or one enum-validation block in the `--mode` case). The semantic change is contained:

- `index rebuild`: pure refactor. The envelope `kind` string `"usage.confirmation_required"` is identical before and after; only the source changes from a string literal to `Kinds.USAGE_CONFIRMATION_REQUIRED`. Phase 6 tests that key on the `kind` string still pass.
- `search --mode`: behavior change. The envelope `kind` changes from `"config.bad_enum"` to `"cli.bad_enum"` and the exit code changes from 2 to 1. Any Phase 5 test that asserts the old values must be updated. Per `005/002.context.md` lines 33–54, Phase 5's planner explicitly recommended deferring this kind classification to Phase 7 — so this is the planned cleanup, not an unexpected breakage.

Coder should verify that no Phase 6 or Phase 5 tests will silently fail by running `uv run pytest` after step 004 and reading the diff. If a prior test asserts the old kind / code, update it inline and note the change in `status.md` under "Files Changed".

## Why `EXIT_USAGE` (1), not `EXIT_CONFIG` (2)

`errors-and-exit-codes.md` "Exit code table":

- Code 1: "usage" — "Argument parsing or usage error."
- Code 2: "config" — "Malformed TOML, schema mismatch, missing required key, version-pin unsatisfied."

`--mode garbage` is an argument-parsing error. The config file's `embed_backend` value not being in the allowed set remains a code-2 / `config.bad_enum` error — Phase 7 leaves that path untouched. The two `bad_enum` paths now have distinct kinds:

- `config.bad_enum` (code 2): TOML key value violates schema.
- `cli.bad_enum` (code 1): CLI flag value violates flag's enum.

This is the additive-discipline correct outcome per `errors-and-exit-codes.md` "Implications":

> Adding a new failure mode is additive — new `kind`, new entry on the table, possibly a new exit code in the relevant decade. No existing agent breaks.

Old agents keying on `code == 2` for `--mode` failures now see `code == 1`. This is a behavior change. Acceptable because:

1. The MVP has not shipped; there are no external agents yet.
2. Phase 5's planner explicitly recorded this as a Phase 7 cleanup target.
3. The `kind` was already going to change (`config.bad_enum` → something CLI-specific); the code follows the category.

## Why not Typer's built-in enum validation alone

Typer's `Literal["bm25", "dense", "hybrid"]` / `enum.Enum` flag types surface a usage error with Typer's own message and exit code 2 by default. That is fine for human users but:

- It does NOT emit our envelope under `--format json` (it emits Typer's text-mode message regardless of `--format`).
- Its `kind` is not addressable — agents cannot key on `cli.bad_enum`.
- Its exit code (2) clashes with the config-error category in our table.

So step 004 wires an explicit pre-validation in `cli_search` that emits `CodeIndexError(EXIT_USAGE, Kinds.CLI_BAD_ENUM, ...)`. Typer's flag still uses `str` (not `Literal`) to avoid Typer's own validation pre-empting ours; the explicit check inside the function body is the validation surface.

The same pattern can be reused if future subcommands grow CLI-flag enums.

## "Phase 6/5 step files already use the new kinds" alternative

The orchestrator flagged that Phase 5/6 plan files were "amended by future planner passes to use the new kinds, OR Phase 7's coder needs to ensure the changes don't regress Phase 5/6 tests" (`context.md` step 004 dependencies note). Phase 7's planning assumes:

- Phase 5 and Phase 6 plan files have NOT been amended (no edit allowed per "Out of scope" in `context.md`).
- The actual code Phase 5 / Phase 6 shipped uses the old kinds (`Kinds.CONFIG_BAD_ENUM` for `--mode`, free-string `"usage.confirmation_required"` for `index rebuild`).
- Step 004 updates the **code** (`cli.py`) and any tests that assert the old kinds. The plan files for Phases 5 / 6 stay as historical record — they are append-only per `docs/plans/CLAUDE.md` lifecycle conventions.

If the coder finds that Phase 5/6 already use the new kinds (e.g. because the architect or a bug-fixer pre-applied the change), step 004 becomes a no-op for the raise sites and the tests; only the `Kinds` registry additions remain. Document the situation in `status.md` notes.

## What this step does NOT do

- Does not add new exit-code constants. The two new kinds share the existing `EXIT_USAGE = 1`.
- Does not retire `Kinds.CONFIG_BAD_ENUM`. It still applies to `embed_backend` TOML validation.
- Does not amend Phase 5 or Phase 6 plan files. Their record of "use `CONFIG_BAD_ENUM`" and "use free-string `usage.confirmation_required`" stays as written; the divergence is recorded in `status.md` "Files Changed" when the coder updates the code.
- Does not change the boundary exception handler. The handler already routes `CodeIndexError` via the envelope writer regardless of `kind`.
