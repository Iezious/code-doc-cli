# Step 003 context — indexer pipeline

## Pipeline shape

For each `WalkedFile` yielded by `walker.walk(root, config)`:

1. Look up the plugin via the Phase 3 registry's extension dispatch
   (`registry.for_extension(walked.extension)` or whatever name the registry
   ships). If no plugin matches, skip silently (the walker should already
   have filtered, but defend in depth).
2. Call `plugin.chunk(walked.path, walked.content)`,
   `plugin.symbols(walked.path, walked.content)`,
   `plugin.imports(walked.path, walked.content)`. Wrap the three calls in a
   single `try` — a plugin raising on any of them means skip the file.
3. Append each chunk's text to a buffer of pending texts; track each
   chunk's metadata (path, language, chunk index) in a parallel list.
4. When the buffer reaches `config.embed_batch_size`, call
   `backend.encode(buffer)` and insert the resulting vectors alongside the
   chunk metadata into `chunks` + `chunks_fts` + `embeddings`.
5. After the walk completes, flush any remaining buffer.
6. Insert symbol and edge rows in their own loop (or interleaved per file
   — coder's call). Use the `chunk_id` from the corresponding chunk
   insert as the FK in `symbols.chunk_id` and `edges.src_chunk_id`.
7. After a file's chunks, symbols, and edges have all been inserted
   successfully, upsert its `files` row (see "Files writes" below).

`dry_run=True` short-circuits at step 4: the encode call is skipped and
no DB inserts happen. Walking and chunking still run so that the per-file
warnings (encoding, plugin raises) still surface and the `IndexerResult`
counts reflect what a real build would have processed. The `files` upsert
at step 7 is also skipped under `dry_run`.

## Auto-rebuild SQL sequence

Before the first insert, count rows in `chunks`. If `> 0`, execute (in a
single transaction):

```sql
DELETE FROM edges;
DELETE FROM symbols;
DELETE FROM embeddings;
DELETE FROM chunks_fts;
DELETE FROM chunks;
DELETE FROM files;
DELETE FROM meta WHERE key IN ('embed_model', 'embed_dim');
```

Six row-data tables are cleared: `chunks`, `chunks_fts`, `embeddings`,
`symbols`, `edges`, `files`. The two indexer-owned `meta` keys
(`embed_model`, `embed_dim`) are reset. Order matters only insofar as FK
constraints might exist (Phase 1's schema is currently FK-less per
`storage.md`, but the order above is also the safe one if FKs are added
later). Do not touch `meta.schema_version` or `meta.code_index_version`.

The "count rows in chunks" probe is enough; we do not need to check the
other tables independently — Phase 1's migration created all of them
together. If the schema has tables but they are empty, no deletes run and
the insert path proceeds.

## Column mappings

Per [`../../architecture/storage.md`](../../architecture/storage.md)'s
schema sketch:

- `chunks` row from a `Chunk`:
  - `path` = `str(walked.rel_path)` (relative to walk root, forward
    slashes — normalize with `Path.as_posix()`).
  - `language` = `plugin.name` (the language plugin's `name` attribute,
    e.g. `"python"`).
  - `project` = `config.project`.
  - `start_line`, `end_line`, `kind`, `name`, `scope`, `content` =
    `chunk.start_line`, `chunk.end_line`, `chunk.kind`, `chunk.name`,
    `chunk.scope`, `chunk.text`.
- `chunks_fts` is a contentless FTS5 mirror of `chunks`. Insert with the
  same `rowid` as the parent `chunks` row; the contentless FTS5 trigger
  pattern from Phase 1's storage helper (if it set triggers up) handles
  this automatically. If Phase 1 did not install triggers, the indexer
  writes both rows explicitly.
- `embeddings` row: `chunk_id = chunks.id`, `embedding = vector`.
- `symbols` row from a `Symbol`: `chunk_id`, `name = symbol.name`,
  `kind = symbol.kind` (`"def"` / `"ref"`), `line = symbol.line`.
- `edges` row from an `Edge`: `src_chunk_id`, `dst_name = edge.target`,
  `kind = edge.kind`, `meta = json.dumps(edge.meta) if edge.meta else
  None`.

## `meta` writes

- `embed_model`: `backend.name` (the protocol-defined name string, e.g.
  `"fastembed:jina-code-v2"`).
- `embed_dim`: `backend.dim` (an int, e.g. `768`). Store as a string in
  the `value TEXT` column; the readers in Phase 5/6 will parse.

## `files` writes

The `files` table is the source of truth for incremental sync (see
[`../../architecture/storage.md`](../../architecture/storage.md)'s
"Sync state" subsection). Phase 4 writes it; Phase 6 `index sync`
reads it.

- **Trigger:** after a file has been successfully chunked AND its
  embeddings, symbols, and edges have all been inserted. A file whose
  plugin raises (per-file try/except above) or whose IO fails does NOT
  get a `files` row.
- **SQL (per file):**
  ```sql
  INSERT INTO files (path, mtime, size)
  VALUES (?, ?, ?)
  ON CONFLICT(path) DO UPDATE SET
    mtime = excluded.mtime,
    size  = excluded.size;
  ```
- **Values:**
  - `path`: the same forward-slash relative path that `chunks.path`
    received for this file (`walked.rel_path` normalized with
    `Path.as_posix()`). If the indexer factored this conversion into a
    helper for `chunks`, reuse it here — `files.path` and `chunks.path`
    must agree byte-for-byte for the Phase 6 join to work. Otherwise
    inline the same `Path.as_posix()` call.
  - `mtime`: `os.stat(absolute_path).st_mtime` (seconds-since-epoch
    float). Stat the same absolute path the walker opened to read
    `walked.content`.
  - `size`: on-disk byte size, either from `os.stat(absolute_path).st_size`
    or `len(walked.content)` if the walker already exposes the raw bytes
    length. Either is acceptable provided it matches the on-disk file.

## Stderr output

- Default level: a single summary line at end of build, e.g.
  `indexed 7 files, 23 chunks in 4.2s`.
- `verbose=True`: a per-file line as each `WalkedFile` finishes, e.g.
  `indexed src/foo.py (3 chunks, 0.08s)`. Warnings (encoding,
  plugin raise, IO error) are emitted at both levels.
- Use the Phase 1 errors module's stderr helper. No bare `print`.

## Warning text shapes

These are not part of the stable contract (cli.md says message text is
not promised stable), but tests will pin the *substring* to detect:

- Plugin raise: `f"plugin {plugin.name} raised on {rel_path}: {exc}"`.
- IO error: `f"io error on {rel_path}: {exc}"`.
- Encoding (raised by the walker, not the indexer): walker's responsibility.

## Connection lifecycle

- Open one storage connection via the Phase 1 helper for the duration of
  `build(...)`. Use a single transaction wrapping the entire build, or
  one transaction per batch — coder's call. WAL mode (Phase 1) makes
  either acceptable.
- Commit before returning `IndexerResult`.

## What this step does NOT do

- Does not run schema migrations directly. The storage open helper does
  that. The indexer assumes the schema is at the latest version once
  `open(...)` returns.
- Does not implement `--strict`. The `build(...)` function has no
  `strict` parameter.
- Does not implement `sync` (Phase 6). Phase 6 will read the `files`
  table this step populates.
- Does not parse the CLI. Step 004 owns the CLI wrapper.
