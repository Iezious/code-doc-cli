# 001 — context

Narrow notes for the query-pipeline step. Feature-wide framing is in
[`context.md`](context.md).

## Synthetic-DB strategy

The unit tests need a SQLite database whose `embeddings` virtual table
has a small dim (e.g. 4) so test vectors stay readable. The Phase 1
schema creates `embeddings` at `FLOAT[768]` (the fastembed default).

Recommended approach for `make_index(tmp_path)`:

1. Call `open_index(tmp_path / "index.sqlite", create_if_missing=True)`
   so migrations run and the full Phase 1 schema is in place.
2. Drop and recreate just `embeddings` at `FLOAT[4]`:
   `DROP TABLE embeddings;` then
   `CREATE VIRTUAL TABLE embeddings USING vec0(chunk_id INTEGER PRIMARY KEY, embedding FLOAT[4]);`
3. Insert rows into `chunks`, `chunks_fts` (or rely on the FTS5
   trigger from `chunks` if migration `0_to_1.py` wired one — the
   Phase 1 schema uses `content='chunks'` so FTS5 reads from `chunks`
   directly; explicit `INSERT INTO chunks_fts(rowid, content, name, scope)`
   rows may be needed depending on the coder's trigger choice. The
   safe path is to `INSERT INTO chunks_fts(chunks_fts) VALUES('rebuild')`
   after inserting `chunks` rows).
4. Insert embeddings rows with hand-picked 4-dim vectors.
5. Write `meta.embed_model = "fake:tiny"`, `meta.embed_dim = "4"`.

This keeps tests independent of the fastembed model download in
Phase 2. If the coder finds a cleaner test-only entry point (e.g.
a `make_test_index(dim=4)` helper that bypasses migrations and
creates the schema directly), that is acceptable — keep it test-only,
not in `src/`.

## sqlite-vec query syntax

The `sqlite-vec` dense query uses MATCH with a serialized vector and
a `k = N` constraint in the WHERE clause. Conceptual SQL:

```
SELECT e.chunk_id, e.distance
FROM embeddings e JOIN chunks c ON c.id = e.chunk_id
WHERE e.embedding MATCH :qvec_bytes
  AND k = :limit
  AND c.language = :lang   -- optional
ORDER BY e.distance
```

The query vector must be serialized to the byte layout `sqlite-vec`
expects (`numpy.ndarray.astype(np.float32).tobytes()` works for the
v0.1 API; verify against the version pinned in `pyproject.toml`).
If the version pinned in Phase 1 uses a different binding, follow
that.

Filters (`c.language`, `c.kind`, `c.path GLOB`) are added to the
same `WHERE` clause; sqlite-vec accepts predicates over joined
tables alongside the MATCH constraint.

## Filter SQL details

- `--lang` → `chunks.language = :lang` (exact match; canonical
  language names from the registry).
- `--kind` → `chunks.kind = :kind` (exact match; the plugin-emitted
  kind string).
- `--path` → `chunks.path GLOB :pattern` (SQLite GLOB; not LIKE).
  Forward-slash paths only, per project conventions.

All filters are parameterized — no string interpolation into SQL.

## `verify_index_compat` placement decision

The helper lives in `code_index.storage` (not inline in `search.py`)
because Phase 6's `symbols` and `graph` subcommands will need the
same loud-fail check before they query. Centralizing avoids
duplication and makes the contract a single line in
`storage.md` once the architect folds it in. Recorded in
[`outcome.md`](outcome.md).

## Mode-skip semantics

- `mode == "bm25"`: skip backend instantiation entirely. Step 002
  must not call `from_config(config)` in this path.
  `verify_index_compat` is also skipped (no dense side runs).
- `mode == "dense"`: instantiate backend, call
  `verify_index_compat`, run dense only.
- `mode == "hybrid"`: instantiate backend, call
  `verify_index_compat`, run both, fuse.

The `search()` function itself only sees `backend: EmbeddingBackend
| None`. The CLI layer (step 002) decides whether to instantiate
and pass it. This keeps `search()` testable with a fake backend or
no backend at all.

## Tie-break

RRF tie-break by "rank in the dense list" per `retrieval.md`:
"Ties broken by rank in the dense list (semantic preferred for
equal contribution)". Implementation: when fused scores are equal
(within float tolerance), the item whose dense-rank is lower wins.
Items missing from the dense list sort after items present in it
on ties.

## Excerpt computation

`SearchResult.excerpt = "\n".join(content.splitlines()[:EXCERPT_MAX_LINES])`.
Trailing newlines are not appended. If the chunk is shorter than 30
lines, the full content is the excerpt.

## What this step does NOT do

- Does not touch `cli.py`. The Typer subcommand body lands in
  step 002.
- Does not run against the polyglot fixture. The synthetic DB is
  enough to exercise the query module. The polyglot fixture is
  the integration test in step 002.
- Does not introduce a `--strict` mode for filter validation. An
  unknown `--lang` value is rejected by the CLI layer (step 002)
  using `LanguageRegistry.names()`; the search module accepts any
  string and runs the SQL filter as-is (it will simply return zero
  rows if the language column never matches).
