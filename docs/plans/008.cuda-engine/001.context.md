# 001 context — Device resolution helper

Narrow notes for this step. Feature-wide semantics live in [`context.md`](context.md).

## Public surface designed for two consumers

The module must serve both step 002 (`FastembedBackend`) and step 004 (`config show`):

- `FastembedBackend` calls `resolve_device(warn=True)` so the requested-cuda-unavailable warning surfaces during a build/search run.
- `config show` needs the raw value with NO probe (`requested_device()`) AND the resolved value with a QUIET probe (`resolve_device(warn=False)`), because `config show` is a diagnostic surface that must never warn or fail on a broken provider.

Keep `requested_device()` (no probe) and `resolve_device()` (probes) as separate entry points for exactly this reason.

## Error kind for invalid env value

Reuse the existing config-validation error path. The codebase already raises `CodeIndexError` for bad config enum values — `embed_backend` validation produces `config.bad_enum` (code `2`); see [config.md](../../architecture/config.md) "Validation rules" and [errors-and-exit-codes.md](../../architecture/errors-and-exit-codes.md). An invalid `CODE_INDEX_DEVICE` is the same class of error (a bad enum from user-controlled input), so raise `CodeIndexError` with kind `config.bad_enum` / exit code `2`. The coder should confirm the exact `Kinds`/exit-code constant names from `src/code_index/errors.py` (or wherever `CodeIndexError`/`Kinds` are defined) when wiring this; do not invent a new code.

## onnxruntime probe isolation

`onnxruntime` may be absent (it is pulled transitively by `fastembed`, but the diagnostic stance requires we tolerate a broken install). Import it lazily inside `available_providers` and wrap both the import and the `get_available_providers()` call so any exception yields `[]`. This is what lets `config show` and `auto` resolution work on a box with a broken onnxruntime.

## Warning wording

The exact stderr warning text is an implementation choice (it is flagged in `outcome.md` as a candidate doc observation). Keep it one line, plain text, naming that `cuda` was requested but the CUDA provider is unavailable and the run is falling back to CPU. Do not prefix with structured/log-level machinery — stderr is plain text in MVP (see [cli.md](../../architecture/cli.md), "Output streams and logging").

## Testing the stderr warning

Capture via pytest `capsys`/`capfd` and assert the warning appears exactly once on the fallback path and is absent on the silent paths.
