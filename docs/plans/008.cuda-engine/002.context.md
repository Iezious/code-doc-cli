## fastembed CUDA invocation

The architecture note (see [embeddings.md](../../architecture/embeddings.md), "Implementation note") states `FastembedBackend` passes `cuda=True` / `providers=[...]` to `TextEmbedding`. fastembed-gpu's `TextEmbedding` accepts `providers=[...]` and/or `cuda=`/`device_ids=` kwargs depending on version. The coder should pass the provider list for the resolved device (CUDA provider list when `cuda`, else leave provider selection to fastembed's CPU default) in a way the installed fastembed accepts. Verify the accepted kwarg names against the installed fastembed at build time; the architecture wording (`cuda=True` / `providers=[...]`) is the intent, not a literal mandate to pass both. Note the exact kwarg used as a candidate `outcome.md` observation if it differs from the doc wording.

## Resolution happens once, in the backend

Resolve via `resolve_device(device, warn=True)` exactly once in `__init__` and store the result. Do NOT re-probe in `encode`. The `warn=True` path is correct here: a build/search run SHOULD warn when `cuda` was requested but unavailable. (`config show` is the quiet consumer — that is step 004.)

The real `FastembedBackend` sets `self.device`, so `test_satisfies_protocol` continues to pass. `@runtime_checkable` only checks method/attribute presence at isinstance time for the attributes it can see; the existing real-backend fixture sets the attribute so the check holds.
