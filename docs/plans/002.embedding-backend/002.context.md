# Step 002 — context

Step-scoped notes for [`002.factory.md`](002.factory.md). Shared framing is in [`context.md`](context.md).

## Why `from_config` lives in its own module, not in `__init__.py`

Keeping `factory.py` separate from `__init__.py` mirrors `fastembed.py` and the future `voyage.py`: every "kind of file" in the package has one job. `__init__.py` is the re-export surface only. This is the layout the architecture pinned for the package — see decision 1 in [`context.md`](context.md).

## Voyage stub raise — kind reuse rationale

`Kinds.CLI_NOT_IMPLEMENTED` was introduced in Phase 1 for unimplemented CLI subcommand stubs. The Voyage stub raise reuses it because:

- It is also a "not implemented in this build" failure.
- Adding a new kind (`feature.not_implemented` or `backend.not_implemented`) would require a `Kinds` registry change in `errors.py` and a corresponding architecture-doc update in `errors-and-exit-codes.md`. Phase 2's scope explicitly does not touch Phase 1 modules.
- The kind is transient — it disappears when Phase 7 lands the real Voyage backend. Inventing a permanent kind for a transient failure is wasteful.

The kind-name "CLI" vs "feature" mismatch is recorded in [`outcome.md`](outcome.md) as a question for the architect to consider when Phase 7 plans, not a question for the Phase 2 coder.

## Mocking `FastembedBackend` in tests

The factory tests must not perform a network download. Two viable patterns:

1. `monkeypatch.setattr("code_index.embeddings.factory.FastembedBackend", spy)` — patches the reference *inside the factory module*, which is what `from_config` resolves. Preferred.
2. `monkeypatch.setattr("code_index.embeddings.fastembed.FastembedBackend", spy)` — patches the source-of-truth reference. Does **not** work if `factory.py` did `from .fastembed import FastembedBackend` (the name is rebound in `factory`'s namespace at import time). Avoid.

Pattern #1 is the safe default. A `unittest.mock.MagicMock(spec=FastembedBackend)` is sufficient as the spy.

## Constructing `CodeIndexConfig` in tests

Two options depending on what is most ergonomic when Phase 1 is in place:

1. **Via `load_config(fixture_path)`** — true to the calling pattern, but requires a TOML fixture per test case and is verbose for a small parameter sweep. Use this for one happy-path test.
2. **Direct Pydantic instantiation** — `CodeIndexConfig(version=">=0.1,<1", embed_backend="voyage", embed_model="voyage-code-3", embed_batch_size=32, ...)`. Bypasses validation that depends on file-system paths (`roots`, `extra_languages`), which is fine for factory tests since they do not care about those fields. Use this for the parameter sweep.

Coder picks. The factory does not care which path produced the config object.

## Why `cache_dir` is not passed by the factory

The factory does not pass `cache_dir`; it lets `FastembedBackend` use the library default (under user home). The architecture has no per-project cache-dir knob, and adding one would require a new config key and an architecture decision. Tests override `cache_dir` directly when constructing `FastembedBackend` (step 001's tests) — not through the factory.

If a project-level cache-dir knob is needed later, it lands as a config-schema change plus an architecture note; not Phase 2's call.
