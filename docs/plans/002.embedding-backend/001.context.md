# Step 001 — context

Step-scoped notes for [`001.fastembed-backend.md`](001.fastembed-backend.md). Shared framing is in [`context.md`](context.md).

## Fastembed API specifics the coder needs to verify on first contact

The architecture doc fixes the *contract* (`name`, `dim`, `encode`) but not the *library API* used to implement it. The coder should consult the installed `fastembed` package to confirm the exact class name and kwargs. Likely entry point (as of mid-2024 versions of `fastembed`):

- Class `fastembed.TextEmbedding(model_name=..., cache_dir=..., threads=...)`.
- `TextEmbedding.embed(texts: Iterable[str], batch_size: int = ...) -> Iterator[np.ndarray]`.

If the installed version's surface differs, prefer the actual library names over what is sketched above. The contract for `FastembedBackend.encode` (returns a single concatenated `np.ndarray` of shape `(N, dim)`) is fixed regardless of the underlying iterator vs array shape.

The `dim` value is exposed by fastembed in different ways across versions (a class attribute, a method, or a value embedded in a model description dict). Whichever it is, read it once at `__init__` time and store on `self.dim`; do not call into fastembed every time `dim` is accessed.

## Short-name rule for `name`

The architecture example pins `"fastembed:jina-code-v2"` for the default model `"jinaai/jina-embeddings-v2-base-code"`. For Phase 2 the coder can hardcode this single mapping (one model is supported in MVP fastembed config; any other model is an opt-in user choice that lands later). A small dict:

```python
_SHORT_NAMES = {
    "jinaai/jina-embeddings-v2-base-code": "jina-code-v2",
}
```

For non-default models, fall back to the part after `/` of the model identifier with any `embeddings-` prefix stripped. The fallback rule is **only documented in code**; tests assert the default-model mapping explicitly.

## The cache directory is a persistent shared asset

`tests/.cache/fastembed/` is the on-disk fastembed model cache for this repo. It is:

- **Gitignored** (`.gitignore` covers `tests/.cache/`), so the ~120MB of ONNX files never enter the repo.
- **Persistent across test runs.** No fixture, no teardown, no autouse cleanup deletes or touches its contents. A fresh checkout pays the ~120MB download cost on first `uv run pytest`; every subsequent run reuses the cached files and is offline-capable.
- **Not a per-test scratch directory.** Treat it as a shared asset of the test suite, not a fixture-managed temp dir. `tmp_path` / `tmp_path_factory` are wrong for this; the path is hardcoded and stable.

CI behavior is out of scope here: cache configuration on CI runners (e.g. actions/cache) is a deployment concern, not a planning one. Record only the local-dev contract.

## The `default_backend` session-scoped fixture is the canonical entry point

Within `tests/test_fastembed_backend.py`, the `default_backend` fixture is the only place a `FastembedBackend(...)` for the default model is constructed for general use. The contract:

- Session scope. Instantiated once per pytest session. Yielded to every test that just needs a working backend.
- Loading the ONNX model into memory is the costly part (1–2 s per instantiation even with a warm disk cache). Sharing the instance across tests keeps the full test file's runtime near the cost of one load.
- New tests in this file should **prefer the fixture over instantiating their own backend**. If a future test needs a different model or a different `batch_size` and option (b) below is not adequate, extend the fixture surface (e.g. add a `small_batch_backend` session-scoped fixture) rather than constructing ad-hoc instances inside test bodies.

The test-isolation contract for this file:

- All tests use `default_backend` **except**:
  - `test_encode_multi_batch` may construct a second backend (one of options (a)/(b)/(c) below).
  - `test_second_instantiation_reuses_cache` **must** construct a fresh backend — that fresh instantiation is the thing under test.
- No other test creates a new `FastembedBackend`. Adding one without extending the fixture surface is a review-blocker.

## Batching test: which option to take

`test_encode_multi_batch` needs `batch_size=4`, which differs from the fixture's default. Three options were considered:

- (a) Parametrize the shared fixture.
- (b) Instantiate a second `FastembedBackend` with the same `cache_dir` so download is skipped, paying only a second in-memory model-load.
- (c) Accept that batching is the one test that pays a second model-load cost (functionally equivalent to (b), framed as a deliberate trade-off rather than a workaround).

**Recommended: option (b).** Rationale: cleanest test isolation, no fixture-parametrization gymnastics that would cascade into every fixture-consuming test, and the second-instance load cost is one-time and small in absolute terms (the ONNX file is already in the OS page cache after the first load, so the second load is bound by deserialization, not disk I/O). The coder may override this and record the alternative choice in the test file's docstring or a test comment if there is concrete justification.

## Cache-reuse assertion form (decision)

The "no redownload on second instantiation" test is filesystem-snapshot based, not timing-based:

- Before the fresh second instantiation, walk `tests/.cache/fastembed/` and record a sorted list of `(relpath, size)` tuples (or equivalently: file count plus total byte size, if the coder prefers a coarser invariant).
- Instantiate a fresh `FastembedBackend(..., cache_dir="tests/.cache/fastembed")`.
- Re-snapshot. Assert the two snapshots are equal.

Equality means: no new files were written, no existing file changed size. Modification-time is not part of the snapshot — some fastembed versions touch metadata even when content is unchanged, and we only care about download-skip, not metadata stability.

Monkeypatching fastembed's internal downloader was considered and rejected: it couples the test to library internals that have shifted across versions.

## Cache directory wiring

The fastembed cache directory is set per-`TextEmbedding`-instance via the constructor kwarg. The session fixture passes `cache_dir="tests/.cache/fastembed"` (forward slashes, relative to repo root). The fixture is responsible only for instantiating the backend; the cache directory will be created by fastembed on first download. Do not pre-create or clean it from test code.

## What this step does NOT do

- Does not raise `CodeIndexError`. If fastembed itself fails (model name unknown, network down on first run), the native exception propagates. Mapping these to `backend.model_download_failed` / `backend.encode_failed` (codes 20) is Phase 7's job and would require touching `errors.py`'s `Kinds` registry to add the missing kinds.
- Does not import from `code_index.config`. The factory in step 002 owns the config-to-backend bridge.
- Does not expose any module-level globals beyond `__all__` in `__init__.py`.

## Note on `runtime_checkable`

`@runtime_checkable` is added to `EmbeddingBackend` so that `isinstance(backend, EmbeddingBackend)` works in tests (and in any future debugging). Be aware that `runtime_checkable` for Protocols only checks attribute presence, not signatures — pyright remains the source of truth for structural compatibility. The test `test_satisfies_protocol` is a smoke check, not a contract assertion.
