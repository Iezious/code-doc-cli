## Placeholder pattern for plugin modules

Step 001's `from_builtins()` must successfully import all seven plugin modules so it can harvest their `LANGUAGE` exports. To keep 001 independently completable (and to keep 002–008 parallelizable), step 001 creates each plugin module with a *placeholder* `LANGUAGE` that has the right `name` and `extensions` but `chunk()` / `symbols()` / `imports()` each return `[]`.

A small helper inside `registry.py` (or a private `_placeholder.py` module — coder's call) avoids duplicating the class shape seven times:

```python
class _PlaceholderPlugin:
    def __init__(self, name: str, extensions: tuple[str, ...]) -> None: ...
    name: str
    extensions: tuple[str, ...]
    def chunk(self, path, content): return []
    def symbols(self, path, content): return []
    def imports(self, path, content): return []
```

Each plugin module then reduces to:

```python
# src/code_index/languages/python.py
from .registry import _PlaceholderPlugin
LANGUAGE = _PlaceholderPlugin("python", (".py",))
```

Steps 002–008 replace the placeholder body — they delete the `_PlaceholderPlugin` line and define a real class, but keep the `LANGUAGE = <RealPlugin>()` export line. The registry contract does not change.

Module → `(name, extensions)` mapping for the placeholders (from `chunking-and-languages.md`):

| Module                                            | name          | extensions                |
|---------------------------------------------------|---------------|---------------------------|
| `src/code_index/languages/python.py`              | `"python"`    | `(".py",)`                |
| `src/code_index/languages/csharp.py`              | `"csharp"`    | `(".cs",)`                |
| `src/code_index/languages/javascript.py`          | `"javascript"`| `(".js", ".mjs", ".cjs")` |
| `src/code_index/languages/typescript.py`          | `"typescript"`| `(".ts", ".tsx")`         |
| `src/code_index/languages/golang.py`              | `"go"`        | `(".go",)`                |
| `src/code_index/languages/fsharp.py`              | `"fsharp"`    | `(".fs", ".fsi", ".fsx")` |
| `src/code_index/languages/lsl.py`                 | `"lsl"`       | `(".lsl",)`               |

Plugin steps 002–008 are bound by these exact name + extension values; do not change them without updating `chunking-and-languages.md` first.

## Error mapping

- `extra_languages` path missing / unreadable → `CodeIndexError(EXIT_CONFIG, Kinds.CONFIG_BAD_PATH, ...)`. Note: Phase 1's config loader already validates path existence and raises this. The registry's `load_extra_language` is the **second line of defense** (race conditions, in-test direct calls). It must produce the same `kind` so the contract is uniform.
- Module imports successfully but has neither `LANGUAGE` nor `LANGUAGES` → `CodeIndexError(EXIT_CONFIG, Kinds.CONFIG_UNKNOWN_LANGUAGE, ...)`. Message names the offending path.
- Module raises during `exec_module` → let the exception propagate. Phase 4 will catch and translate. Phase 3 does not invent a new `kind` for this.

## `active_plugins` ordering

`active_plugins(config)` returns plugins in this order: built-ins (in the hard-coded order of `from_builtins()`) first, then `extra_languages` in the order listed in config. After `filter_active`, the relative order is preserved. Tests asserting `.names()` order rely on this.

## syrupy configuration

`syrupy>=4` only. No `pyproject.toml` plugin configuration block needed — syrupy auto-discovers tests via the `snapshot` fixture. Snapshot files default to `tests/__snapshots__/test_<lang>_plugin.ambr`. The first run of any plugin test in steps 002–008 generates the snapshot via `pytest --snapshot-update`. Step 001 does not produce or commit any `.ambr` file itself.

## Out of scope for 001

- Real `chunk` / `symbols` / `imports` behavior for any language — handled in 002–008.
- Phase 4 plugin-error skip/strict policy — Phase 4's indexer wraps plugin calls; this step's plugins never raise on bad content.
- Per-plugin config sub-tables (e.g. `[code_index.languages.lsl]`) — anticipated by `config.md` but not implemented here; surfaced in [`outcome.md`](outcome.md) as an architect question.
