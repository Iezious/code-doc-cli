## Parser

Hand-rolled. No tree-sitter F# grammar is mature enough; per the architecture doc, "not worth the dependency drama". Approach:

1. Tokenize line-by-line.
2. Track an indentation-aware scope stack: `namespace`, `module`, `type`, `member`.
3. Regex-match the start of each construct (`^\s*(let|let rec|member|type|module|namespace)\b`).
4. End each chunk at the next sibling-or-shallower construct, or at EOF.
5. Strip leading attributes (`[<...>]`) and doc comments (`///`) but include them in the chunk text.

This is fragile by design — F# is genuinely hard to parse. The snapshot test is the regression gate. Edge cases that trip the regex (e.g. `let` inside an expression, computation-expression syntax) should *not raise*; they should at worst produce an over-large or under-large chunk. Phase 4+ can revisit.

## `.fsproj` discovery

From `path`:

1. Walk up parents from `path.parent` until `path.parent.parents` is exhausted or until a depth limit (6) is reached.
2. At each level, look for any `*.fsproj` file.
3. If found, parse via `xml.etree.ElementTree`, extract every `<Compile Include="..." />` value, resolve each to an absolute path relative to the `.fsproj`'s directory, and store the order.
4. Cache the resulting `{compile_path -> order}` dict on the plugin instance, keyed by the `.fsproj`'s absolute path. The cache persists for the lifetime of the plugin (and the process).

If no `.fsproj` is found, the plugin's per-file warn helper emits one `write_log_stderr` line. To avoid spamming, the plugin remembers which directories it has already warned about and only emits once per *directory* (the file-level cache key).

## Recording `fsproj_order`

Pick **one** storage form and use it consistently:

- Option A: append to `scope` as `"Geometry|fsproj=3"`. Pros: zero new fields. Cons: parsing apparatus on the consumer side.
- Option B: stuff into a sentinel string field appended to the chunk text — clearly the wrong choice; rejected.
- Option C: store separately as `Chunk.scope` plus a side-channel `dict` returned by a helper — rejected; this would require widening the Protocol.

Option A is recommended but not mandated. Snapshot pins whichever the coder picks. If the coder finds a cleaner form within the existing `Chunk` shape, document it in `outcome.md` so the architect can decide whether to surface it in the architecture doc.

When the `.fsproj` lookup misses or the file is not listed, the `fsproj_order` is simply absent from `scope` (no `|fsproj=` suffix).

## Discriminated union cases

```fsharp
type Color =
    | Red
    | Green of int
    | Blue of name: string
```

Emits four symbols:

- `"Module.Color"` (the type itself, `kind="def"`).
- `"Module.Color.Red"` (`kind="def"`, line of `Red`).
- `"Module.Color.Green"` (`kind="def"`, line of `Green`).
- `"Module.Color.Blue"` (`kind="def"`, line of `Blue`).

The chunk for `type Color = ...` is a single chunk of kind `"type"`; the four symbols all reference lines within that chunk.

## `open` directives

`open Foo.Bar` → `Edge(target="Foo.Bar", kind="import", line=L, meta=None)`. `open type Foo.Bar` (F# 5+) → same edge, no special meta — F# `open type` is a binding nuance, not a different kind of import.

## Computation expression definitions

`type FooBuilder() = ...` followed by `let foo = FooBuilder()` — the type definition is chunked as `"type"`. The `let foo = ...` binding is chunked as `"function"` (matching the architecture doc's "Computation expression definitions get their own chunk"). The snapshot pins the exact behavior.

## Error tolerance

Never raise. On a regex-parse miss, log nothing (the warning path is for the missing `.fsproj`, not for individual parse misses) and either skip the offending region or produce a best-effort chunk.

## Out of scope

- Type inference.
- Inline-IL parsing.
- Active patterns beyond basic chunking.
- `#load`, `#r` directives in `.fsx` scripts — Phase 3 ignores them; Phase 6 may revisit if seam analysis needs them.
- `ref` symbols.
