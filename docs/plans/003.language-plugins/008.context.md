## OSSL deferral

Per user-confirmed decision in [`context.md`](context.md): Phase 3 LSL recognizes pure LSL only. No `osXxx` calls are recognized as `ref` symbols or as edges. The architecture doc currently says "an opt-in flag in plugin config enables `osXxx` recognition" — that flag does not exist in Phase 1's config schema and is not being added in Phase 3. [`outcome.md`](outcome.md) flags this for the architect.

The plugin's regex for `ref` symbols is `\bll([A-Z][A-Za-z0-9]*)\b` — the leading `ll` is mandatory. Any `os` prefix is excluded by virtue of not matching. The test `test_no_ossl_recognition` is the regression gate.

## Parser

Hand-rolled, regex + brace-balance state machine. LSL grammar:

- A file is a sequence of: globals (variable declarations, function definitions) followed by exactly one `default` state and zero or more named states.
- A state is `state <name> { <event-handlers> }`. The `default` state uses the keyword `default` instead of `state default`.
- An event handler is `<event-name>(<params>) { <body> }`.
- A user function is `<return-type> <name>(<params>) { <body> }` at global scope. LSL return types: `integer`, `float`, `string`, `key`, `vector`, `rotation`, `list`, or none (void function: just `<name>(<params>) { ... }` — but this conflicts with event-handler syntax; user functions are unambiguously at global scope, not inside a state).

Approach:

1. Strip line comments (`//...`) and block comments (`/* ... */`) before scanning. Preserve line numbers via newline-preserving replacement.
2. Track brace depth. At depth 0, identify `state X` / `default` / `<type> <name>(...)` / `<type> <name> = ...;` boundaries.
3. Inside a state (depth 1), identify event handlers by matching against a known LSL event-name set OR by the generic `<ident>(<params>) {` pattern at depth 1. (A known-event whitelist is safer; LSL has a fixed set of event names.)
4. Capture each construct's start_line/end_line and the source text between them.

Edge extraction is a second pass over the chunk text: scan for `llListen(`, `llMessageLinked(`, `llHTTPRequest(`, `llEmail(` and extract the first argument by balanced-paren scan.

## Symbol naming and `ref` extraction

`def` symbols:

| Source                                   | Symbol                                                       |
|------------------------------------------|--------------------------------------------------------------|
| global variable `integer counter = 0;`   | `Symbol(name="counter", kind="def", line=L)`                 |
| user function `integer add(integer x)`   | `Symbol(name="add", kind="def", line=L)`                     |
| event handler `touch_start` in `default` | `Symbol(name="default.touch_start", kind="def", line=L)`     |
| event handler `state_entry` in `idle`    | `Symbol(name="idle.state_entry", kind="def", line=L)`        |

`ref` symbols: every match of `\bll([A-Z][A-Za-z0-9]*)\s*\(` in the file emits one `Symbol(name="llXxx", kind="ref", line=L)`. Duplicates across the file are kept (one per call site). The match anchors on `\b` so substrings inside identifiers (`myllListen`) don't match.

## Edges — argument extraction

For each of the four edge-producing `llXxx` calls, the `target` is the source text of the **first** argument expression, verbatim (whitespace-trimmed). Use a small balanced-paren / balanced-bracket / balanced-quote scan starting at the `(` to find the first top-level `,` or matching `)`. The text between the `(` and that boundary is the target.

Examples:

| Call                                      | `target`                       |
|-------------------------------------------|--------------------------------|
| `llListen(42, "", NULL_KEY, "")`          | `"42"`                         |
| `llListen(channel, "", NULL_KEY, "")`     | `"channel"`                    |
| `llMessageLinked(LINK_THIS, 1, "hi", "")` | `"LINK_THIS"`                  |
| `llHTTPRequest("https://x.example", [], "")` | `"\"https://x.example\""` (the literal as written, quotes included) |
| `llEmail(addr, "subject", "body")`        | `"addr"`                       |

Note `llHTTPRequest` and `llListen` differ in which argument is "the interesting one" by convention (channel vs URL); for Phase 3 we use the first argument uniformly and let the consumer interpret. Snapshot pins.

## Edge kinds

Exactly four edge kinds for this plugin:

- `"listen"` from `llListen`.
- `"link_message"` from `llMessageLinked`.
- `"http"` from `llHTTPRequest`.
- `"email"` from `llEmail`.

No other `llXxx` produces an edge in Phase 3. (`llRegionSay`, `llInstantMessage`, etc. are interesting but not in scope; they would arguably belong under `"listen"`-adjacent kinds, but the architecture doc is silent — defer.)

## Imports

`imports()` returns `[]`. LSL has no traditional imports. The architecture doc says explicitly: "A plugin returning empty lists is valid (e.g., LSL has no imports in the traditional sense)."

## Fixture outline

`tests/fixtures/languages/lsl/sample.lsl`:

```lsl
integer counter = 0;
string name = "widget";

integer add(integer x, integer y)
{
    return x + y;
}

default
{
    state_entry()
    {
        llSay(0, "ready");
        llListen(42, "", NULL_KEY, "");
        osSetSpeed(1.0);    // must NOT appear in symbols or edges
    }

    touch_start(integer n)
    {
        llMessageLinked(LINK_THIS, 1, "touched", "");
        llHTTPRequest("https://example.invalid/x", [], "");
        llEmail("dest@example.invalid", "hello", "body");
    }
}

state idle
{
    state_entry()
    {
        llSay(0, "idle");
    }
}
```

This exercises every chunk kind, the `<state>.<event>` symbol form, all four edge kinds, both `ll` and `os` prefixes for the absence test, and the `default` vs named-state distinction.

## Error tolerance

Never raise. Malformed brace nesting → return whatever chunks the scanner gathered before the error point. Add no warnings (silent best-effort; Phase 4 decides whether to surface).
