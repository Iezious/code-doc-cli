# Step 003 context — symbols

## Case-sensitive LIKE

SQLite's `LIKE` is case-insensitive for ASCII by default (`'Foo' LIKE 'foo'` is true). Phase 6 needs case-sensitive matching per `chunking-and-languages.md` ("Symbol identity" → "Case-sensitivity").

Three equivalent ways to get case-sensitive matching; pick **option (a)**:

(a) `PRAGMA case_sensitive_like = ON;` on the connection at open time. Affects every `LIKE` on that connection. **This is the Phase 6 choice** because it affects exactly the read-only query paths in steps 003 and 004 and never the indexer (the indexer never uses `LIKE`). Apply the PRAGMA inside `query_symbols` (and the graph counterpart) right after they obtain the connection — or, if the `_preflight` helper is shared, apply it there once.

(b) Use `GLOB` instead of `LIKE`. `GLOB` is case-sensitive by default; the substring pattern becomes `*name*` rather than `%name%`. Functional, but the SQL diverges from what `cli.md` and `context.md` document.

(c) Use the `ESCAPE` clause to suppress wildcards in user input — irrelevant to case sensitivity, listed only to clarify it is not the answer.

The PRAGMA is connection-scoped, not database-scoped; it does not persist across connections, so the indexer (Phase 4) is unaffected.

## LIKE wildcard escaping

User-supplied `name` may contain literal `%` or `_` characters. SQLite's `LIKE` treats these as wildcards. For substring matching the safe form is:

```python
escaped = name.replace("\\", "\\\\").replace("%", "\\%").replace("_", "\\_")
pattern = f"%{escaped}%"
# SQL: WHERE symbols.name LIKE ? ESCAPE '\\'
```

For exact matching, use `=` (not LIKE) and bind `name` directly — no escape concerns.

This escaping is a robustness detail, not a contract requirement. The coder may skip it for MVP if the test cases do not exercise `%` / `_` in symbol names; the polyglot fixture does not have any such names. Document the chosen approach in the implementation.

## Parameter binding

Build the parameter list dynamically depending on whether `--lang` is set:

```python
sql = """
    SELECT chunks.path, chunks.scope, chunks.language, symbols.name, symbols.line
    FROM symbols
    JOIN chunks ON symbols.chunk_id = chunks.id
    WHERE symbols.kind = ? AND symbols.name {op} ?
"""
params: list = [kind, pattern_or_name]
if language is not None:
    sql += " AND chunks.language = ?"
    params.append(language)
sql += " ORDER BY chunks.path, symbols.line"
```

Where `{op}` is `LIKE` for substring or `=` for exact. Both forms are parameterized — no f-string interpolation of user input into the SQL body.

## Why the engine emits empty result on no hits

`cli.md`'s output discipline section says "search returning zero results is not an error". The same applies to `symbols` and `graph`. Exit 0; empty list (or empty stdout) is the success response.

## Text output format

Pin one shape so the verifier knows what to grep:

```
<path>:<line> [<language>] <name>      (scope: <scope>)
```

If `scope` is `None`, omit the trailing parenthesized part:

```
<path>:<line> [<language>] <name>
```

The exact spacing is not contractual (per `errors-and-exit-codes.md`, message text is not promised stable); the test asserts `<path>:<line>` appears and `<name>` appears on the same line. The JSON shape is the stable surface; text is for humans.

## What this step does NOT do

- Does not introduce `--limit` (decision 3).
- Does not collapse duplicate symbols. Multiple `chunks` rows containing the same `name` produce multiple `SymbolHit` entries; `scope` distinguishes them.
- Does not normalize names. The `name` strings in the DB are plugin-emitted verbatim (per `chunking-and-languages.md`, "Symbol identity") and the query returns them unchanged.
