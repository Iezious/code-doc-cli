# Step 004 context — graph

## Edge resolution is lazy

Per `storage.md` ("Edge resolution"), edges are stored as `(src_chunk_id, dst_name, kind, meta)` with no foreign key to `symbols`. Resolution happens at **query time** by joining `edges.dst_name` against `symbols.name`.

`graph callers <symbol>` does the join-with-filter implicitly: the user's `symbol` argument is matched against `edges.dst_name` directly (not `symbols.name`). This is by design — the user is asking "which call sites point at this name?", regardless of whether the engine could resolve the target to a `symbols` row.

`graph deps <path>` does not join `symbols` at all: it returns the raw `(kind, dst_name, meta)` tuple from `edges`. The caller decides what to do with unresolved targets.

If a future step wants "resolved-only" filtering (semi-join `edges.dst_name` against `symbols.name`), it adds a flag. Phase 6 does not add it (decision 3 — no new flags).

## Why `deps` is path-exact and `callers` is name-substring

The two arguments have different semantics:

- **`graph deps <path>`** is "show me the outbound edges from a specific file". The path is a concrete identifier; users will paste it from `grep` output or from an `index sync` summary. Substring matching would conflate distinct files; globbing would be a new mini-language. Exact equality is the only sane MVP behavior. (Decision 4.)
- **`graph callers <symbol>`** is "show me edges pointing at any symbol whose name matches X". Symbols have many lexical forms across languages (`Module.method`, `default::index`, `state.event`); substring is the discoverability lever. Same matching rule as `symbols defs|refs` per `cli.md`.

## `meta` is opaque in Phase 6

The `edges.meta` column is a JSON string written by plugins. Phase 6's `graph deps` surfaces it as-is, without parsing. Reasons:

- Schema does not pin a `meta` shape per `kind` — each plugin defines its own.
- Phase 7's JSON polish pass owns "should `meta` be a nested object or a string?". Phase 6 keeps the safest answer: string-or-null.

Under `--format text`, `meta` is omitted from the human output entirely. Adding it would clutter the line for the common case (most edges have `meta = null`); the JSON channel is the place to consume `meta`.

## Path normalization on input

The user types a path. Phase 6 does **not** rewrite it:

- No `.as_posix()` conversion. If the user types `src\foo.py` on Windows, that does not match `src/foo.py` in the DB. This is acceptable — the engine's canonical path form is forward slashes, and that is what `chunks.path` contains.
- No leading-slash stripping. The DB stores project-root-relative paths (no leading slash). A user typing `/src/foo.py` will get an empty result, which is exactly correct.

Document this in the CLI help text: "path must match exactly; use the forward-slash relative path printed by `index sync` or by `chunks.path`".

## Parameter binding

Same dynamic-LIKE-or-equality pattern as step 003. For deps, the path is always equality:

```python
sql_deps = """
    SELECT chunks.path, edges.kind, edges.dst_name, edges.meta
    FROM edges
    JOIN chunks ON edges.src_chunk_id = chunks.id
    WHERE chunks.path = ?
"""
params: list = [path]
if language is not None:
    sql_deps += " AND chunks.language = ?"
    params.append(language)
sql_deps += " ORDER BY chunks.path, edges.kind, edges.dst_name"
```

Same `PRAGMA case_sensitive_like = ON` choice as step 003 for the callers substring path. Step 003's `003.context.md` documents the PRAGMA decision; step 004 inherits it.

## What this step does NOT do

- Does not resolve `dst_name` to `chunks.path` for callers (no second join to `symbols.chunk_id`). The contract returns the source chunk, not the target chunk. If a future "resolved targets" feature is added, it picks up the symbols join then.
- Does not introduce `--limit` (decision 3).
- Does not parse `meta`. Surface raw or `None`.
