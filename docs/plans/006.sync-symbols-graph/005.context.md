# Step 005 context — DoD integration

## mtime-advance technique

On fast filesystems (NTFS, modern ext4), writing twice to the same file within a millisecond can leave `st_mtime` unchanged. The Phase 4 indexer reads `st_mtime` after the write, so the indexer's value matches the post-write disk value — but on sync, the comparison `walked_mtime == files_table_mtime` can be `True` despite the user editing the file.

The test must force a real mtime difference. Two safe approaches:

1. **`os.utime(path, (now + 1, now + 1))`** after writing the new content. This guarantees a forward-jumping mtime.
2. **`time.sleep(0.01)` between the build and the edit.** Less deterministic; not recommended.

Pick approach (1). The test is explicit about advancing time rather than relying on filesystem resolution.

If the test wants to exercise the **size-only-changed** branch of the sync algorithm, it must do the inverse: edit the file (change byte count) then `os.utime(path, (original_mtime, original_mtime))`. The DoD scope does not require this; step 001's unit tests cover the size-only branch.

## Reading "actual" names from the fixture

The polyglot fixture's source files are owned by Phase 4 (step 004 of `004.walker-and-build/`). Their content is fixed but not pinned in Phase 6's plans. To avoid coupling this DoD test to Phase 3 plugin conventions (e.g. "python's `Python` plugin emits dotted scopes including `<module>`"), the test:

- Adds `newly_added_symbol` (definitely a `def`) and queries for it by name — this name is owned by the test, not the fixture.
- For `symbols refs` and `graph callers`, reads candidate names from the DB itself: `SELECT name FROM symbols WHERE kind='ref' LIMIT 1` to pick a ref symbol; `SELECT dst_name FROM edges LIMIT 1` to pick an edge target. Then queries the CLI with that name and asserts at least one hit comes back.
- For `graph deps`, uses `main.py` (the file the test mutated) — that file is guaranteed to be in `chunks.path`.

This pattern makes the DoD test resilient to fixture / plugin changes: it asserts the *contract* (queries work end-to-end) rather than the *content* (a specific symbol exists).

## Why this test uses `CliRunner` rather than calling the engine directly

The phase DoD is a behavior contract about the CLI. Calling `sync.sync(...)` directly would skip:

- Config discovery.
- The pre-flight check.
- The error envelope handling.
- The output stream discipline (stdout vs stderr).
- Argument parsing and the `--format json` codepath.

The DoD test is the only place every CLI surface is composed end-to-end, so it must drive the binary through `CliRunner` (or `subprocess.run([sys.executable, "-m", "code_index", ...])` if the coder wants real-process isolation). `CliRunner` is the Phase 1 convention; stick with it.

## fastembed cache

The Phase 2 contract sets up `tests/.cache/fastembed/` as the model cache directory. CI runs cold once; warm thereafter. This is acceptable for the DoD test; mark it as a slow test (`@pytest.mark.slow` if the project uses that pattern; otherwise just leave it as a normal test — the Phase 4 DoD test already exercises this).

## What this step does NOT do

- Does not introduce a new fixture. Reuses the Phase 4 polyglot.
- Does not exercise `--strict` (deferred).
- Does not exercise Voyage (Phase 7).
- Does not check `code_index doctor` (deferred to v1.1).
- Does not test concurrency. WAL mode is exercised implicitly; the test is single-threaded.
