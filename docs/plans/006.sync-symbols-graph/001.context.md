# Step 001 context — sync engine

## Per-file insert decomposition

The sync engine needs to insert rows for one file at a time (new or changed). Phase 4's `indexer.build(...)` does this for many files inside one call; Phase 6 needs the same logic exposed at single-file granularity.

The coder picks one of two shapes — both acceptable; whichever is easier to land cleanly:

1. **Refactor `indexer.py`** to extract a private helper `_insert_one_file(conn, walked, plugin, backend, config) -> tuple[int, int, int]` (returning `(chunks_inserted, symbols_inserted, edges_inserted)`), and call it from both `indexer.build`'s loop and from `sync.sync`. This is the cleaner outcome but touches Phase 4 code; do this only if the refactor is small and obviously equivalent.
2. **Reimplement the per-file insert inside `sync.py`** using the same SQL column mapping documented in `docs/plans/004.walker-and-build/003.context.md` ("Column mappings", "`files` writes"). Verbose but Phase-6-local.

Either way, the column mapping is fixed:

- `chunks(path, language, project, start_line, end_line, kind, name, scope, content)` — `path = walked.rel_path.as_posix()`, `language = plugin.name`, `project = config.project`, rest from the `Chunk` dataclass.
- `chunks_fts` — same `rowid` as the parent `chunks` row (contentless FTS5 mirror; Phase 1 may have installed triggers, in which case this is automatic — defend in depth by inserting explicitly if needed).
- `embeddings(chunk_id, embedding)` — vector from `backend.encode([text])[0]`.
- `symbols(chunk_id, name, kind, line)` — direct copy from `Symbol`.
- `edges(src_chunk_id, dst_name, kind, meta)` — `dst_name = edge.target`, `meta = json.dumps(edge.meta) if edge.meta else None`.
- `files(path, mtime, size)` upsert at the end (after chunks/symbols/edges for the file all succeeded). `mtime = os.stat(walked.path).st_mtime`, `size = os.stat(walked.path).st_size`.

Plugin raise and per-file IO error are treated the same as in Phase 4: skip + stderr warning + continue + no `files` row for that file. Note: in Phase 6 "skip" on a *changed* file leaves the old rows alone (we never called `delete_file_rows` for it because the chunk step raised before any delete). The coder must order operations so that `delete_file_rows` runs **only after** the new chunks/symbols/edges have been successfully chunked (text-extraction succeeded and the plugin did not raise) — otherwise a plugin raise during sync would leave the file with no rows at all. Concretely: run the plugin first, batch up the new rows in memory, only then call `delete_file_rows` and insert.

## Pre-flight check sequence

This sequence is shared by step 001 (sync), step 003 (symbols), and step 004 (graph). Step 001 is the first place it lands; later steps reuse the same helper.

```python
def _preflight(ctx_obj) -> tuple[CodeIndexConfig, Path, sqlite3.Connection, EmbeddingBackend]:
    config_path = ctx_obj.get("config") or discover_config_path(Path.cwd())
    config = load_config(config_path)
    project_root = config_path.parent.parent  # docs/.helpers/config.toml -> project root
    db_path = config_path.parent / "index.sqlite"
    if not db_path.exists():
        raise CodeIndexError(
            EXIT_INDEX_MISSING, Kinds.INDEX_MISSING,
            f"no index found at {db_path.as_posix()}; run `code_index index build`",
        )
    conn = open_index(db_path)
    backend = embeddings.from_config(config)  # may raise; lets EXIT_UNKNOWN handle (decision 6)
    stored_model = get_meta(conn, "embed_model")
    stored_dim = get_meta(conn, "embed_dim")
    if stored_model != backend.name:
        raise CodeIndexError(
            EXIT_INDEX_MODEL, Kinds.INDEX_EMBED_MODEL_MISMATCH,
            f"index built with embed_model={stored_model!r}, config wants {backend.name!r}; "
            "run `code_index index rebuild`",
            {"stored": stored_model, "configured": backend.name},
        )
    if stored_dim != str(backend.dim):
        raise CodeIndexError(
            EXIT_INDEX_MODEL, Kinds.INDEX_EMBED_DIM_MISMATCH,
            f"index built with embed_dim={stored_dim!r}, config wants {backend.dim!r}; "
            "run `code_index index rebuild`",
            {"stored": stored_dim, "configured": str(backend.dim)},
        )
    return config, project_root, conn, backend
```

Place this helper either:

- as a module-level `_preflight` in `cli.py` (smaller blast radius, no new module), or
- as `code_index.indexutil._preflight` if the coder prefers; the step files for 003/004 reference whichever location is chosen.

The exact location is the coder's call; the contract is that 003 and 004 reuse the same helper rather than duplicating the four-check sequence.

`symbols` and `graph` need the same helper but do **not** need `backend`. The coder may split into `_preflight_no_backend` (skips the embed-model/dim check — wrong, those checks are part of the contract per decision 7) or leave the backend object unused in those subcommands. The latter is simpler; the backend instantiation is cheap once the fastembed model is cached, and the model/dim check requires reading the backend's `name` and `dim` anyway.

## mtime comparison precision

Filesystems differ on mtime resolution (POSIX = nanoseconds via `st_mtime_ns`; FAT32 = 2-second granularity). The `files` table stores `mtime REAL` — `os.stat().st_mtime` as a float. Exact `==` comparison is fine because both sides come from the same `os.stat()` call format. Do not introduce tolerance; if a file is touched in a way that the FS does not record, that is a known mtime+size limitation (decision 1 accepts this).

Size comparison is exact integer equality.

## Walked-set / files-map join

The two sides of the join:

- **Walked set** keyed by `walked.rel_path.as_posix()` → `WalkedFile` instance. Use a dict so we can look up the walker output by path during the `files`-table scan in step 4.
- **`files` map** keyed by `path` (TEXT, already forward-slash) → `(mtime, size)` from the row.

The join is "walk both sides once": iterate the walked set (steps 3a/3b/3c), then iterate `files`-map keys not present in the walked set (step 4).

## Verbose output

Step 001 uses the same per-file verbose pattern as Phase 4's `indexer.build`:

- Default: a single summary line at the end via `write_log_stderr`.
- `--verbose`: per-file line as each file is processed, e.g. `synced src/foo.py (added)`, `synced src/bar.py (changed, 3 chunks)`, `synced src/baz.py (unchanged)`, `removed src/quux.py`.

No bare `print`; use the Phase 1 stderr helper.

## Connection lifecycle

One connection for the whole `sync.sync(...)` call. Wrap the per-file insert + per-file delete in transactions (one per file is fine; one big transaction is also fine — coder's call). Commit before returning. The CLI wrapper closes the connection in a `finally`.
