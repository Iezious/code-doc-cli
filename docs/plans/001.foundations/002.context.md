# Step 002 — context

## Authoritative source

[`../../architecture/errors-and-exit-codes.md`](../../architecture/errors-and-exit-codes.md) is the contract. The exit-code table and the "Enumerated failure surface" subsections are the source of truth for every constant and `kind` string this step defines.

## New kind being added

This feature adds one new entry to the failure surface: `cli.not_implemented` (code 1, category "usage"). It is a transient surface — entries are consumed as later phases implement each subcommand. Recorded in [`outcome.md`](outcome.md) for the architect to apply.

## Envelope shape — full example for assertion

From `errors-and-exit-codes.md`:

```json
{
  "error": {
    "code": 2,
    "kind": "config.version_mismatch",
    "message": "engine 0.5.1 does not satisfy pin '>=0.3,<0.5' in docs/.helpers/config.toml",
    "detail": {
      "pin": ">=0.3,<0.5",
      "engine_version": "0.5.1"
    }
  }
}
```

Tests should assert structural equality of the envelope dict, not byte-level equality of the serialized JSON (key ordering in `json.dumps` is stable but the test should not depend on whitespace).

## Stream discipline reminder

- `write_result_stdout` and `write_error_envelope_stdout` are the only callers of `sys.stdout`.
- `write_log_stderr` and `write_error_summary_stderr` are the only callers of `sys.stderr`.
- Config (003), storage (004), and CLI (005) call these helpers. They never call `print()` directly. Catching this in code review is part of every later step's DoD.

## No backend / parsing / io kinds are raised in Phase 1

They are listed in the registry for completeness (so later phases do not have to re-edit `Kinds`), but no Phase 1 code path raises them. Tests only assert presence + correct dotted-string value, not behavior.
